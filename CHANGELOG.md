## 9.0.0-prerelease

### Breaking

- `Create.PrimaryKey().OnTable("Table").Column("Id")` now generates the constraint name `PK_Table` instead of `PK_Table_Id`, so it matches the name generated by `Create.Table("Table").WithColumn("Id").AsInt32().PrimaryKey()`. Migrations that relied on the old name (for example to drop the constraint later) must either name the primary key explicitly or replace `DefaultPrimaryKeyNameConvention` with a custom `IPrimaryKeyNameConvention` (Issue #1800)
- A connection string that consists only of whitespace is now treated like an empty connection string: the runner switches to connectionless mode instead of handing the connection string to the ADO.NET provider (which previously failed when the connection was opened). Requesting a connection while no connection string is configured now fails with an `InvalidOperationException` when the connection is created, instead of a provider-specific error when it is opened.
- The Firebird processor rejects connection factories whose `OwnsConnection` is `false`: it must close and reopen its connection when committing transactions to release Firebird metadata locks, which is not possible with an externally owned connection.
- Schema checks without a schema (`Schema.Table(...).Exists()`, `Schema.Sequence(...).Exists()`, and the column, index and constraint checks under `Schema.Table(...)`) now look in the convention set's default schema, the one `Create.Table(...)` uses, instead of the provider's fallback (`public` on PostgreSQL, `dbo` on SQL Server, the login's own schema on Oracle). `Schema.Schema("x").Exists()` still checks `x` as written, as `Create.Schema("x")` creates it. With a default schema configured (`DefaultConventionSet("app", ...)` or `--default-schema-name`), an idempotent migration used to miss what it had created and create it again. The schema comes from the new `IDefaultSchemaNameResolver` service, which the runner registers on top of `IConventionSet`. The docs section "Which schema the checks look in" (Advanced > Conditional logic) explains which schema each provider checks and creates in, including two cases a default schema avoids: PostgreSQL sequences with no schema, and Db2 checks with no schema, which match an object of that name in any schema (Issue #1055 by @OlegUfaev; reproduced on PostgreSQL and diagnosed by @RaphaelFakhri)

### New

- Application locking: register an `IApplicationLocker` with `ConfigureApplicationLocker<T>()` so that only one application instance migrates a database at a time. The lock covers version-table creation as well as every runner operation and migration scope (Issue #1949 by @cristiproj; design review by @RaphaelFakhri)
  - Ownership is per dependency-injection scope (`IApplicationLockLease`), counted, and independent of threads and `ExecutionContext`, so implementations do not need to be reentrant
  - Synchronous and asynchronous acquisition with cancellation; `ApplicationLockerOptions.AcquireTimeout`; failures surface as `ApplicationLockException`
  - `Rollback`, `RollbackToVersion` and `MigrateDown` now reload the version info before choosing which migrations to revert, as `MigrateUp` already did, so they act on what the database holds once the lock is taken rather than on what an earlier load saw
- Analyzer `FM0007` warns when a raw `$(name)` token in `Execute.Sql` receives a `DateTime` or `DateTimeOffset` value, which renders as `07/28/2026 13:45:06` and is read differently by different databases. Its code fix rewrites the token to `$[name]`, which formats the value through the provider's quoter (ISO 8601 on most providers, `to_date(...)` on Oracle; an Oracle `DateTimeOffset` still depends on `NLS_TIMESTAMP_TZ_FORMAT`). What `$(name)` emits is unchanged (Issue #2354 by @jzabroski; documented in PR #2401 by @RaphaelFakhri)
- Connectionless scripts for a new database: `RunnerOptions.PreviewFromNothing` also emits the SQL that creates the version table, so a `--no-connection --preview` script can be run against an empty database. It runs after `BeforeAll` maintenance, as a live run does, and creates the version schema only when `IVersionTableMetaData.OwnsSchema` is `true` and the schema is not one every new database has (`dbo`, `public`; an unquoted name is compared the way the database folds it, and on SQL Server `DBO` in another case is created only if the database collation doesn't find it). It throws when the run could execute SQL against a database or has a `StartVersion`, and for rollback, migrate down, listing migrations and validating their order, which an empty database has nothing to revert, list or validate (Issue #2087 by @stambunan; PR #2370 by @Copilot)
  - dotnet-fm: `--preview-from-nothing`; Migrate.exe: `/previewFromNothing`
  - MSBuild `Migrate` task: `PreviewFromNothing`, and the `NoConnection` property it needs, which the task did not expose before
  - Reusable `migration-preview.yml` workflow: the `preview_from_nothing` input scripts each ref for an empty database, and makes the `connection_string` secret optional
- New `IPrimaryKeyNameConvention` (implemented by `DefaultPrimaryKeyNameConvention`) applies the primary key naming convention to both column-level primary keys and standalone primary key constraints, and makes the convention easier to discover and replace (Issue #1800)
- Custom connections: `IMigrationConnectionFactory` allows applications to supply fully configured `IDbConnection` instances to the migration runner (PR #2268 by @Sherif-Ahmed, building on PR #2002 by @Merlin-Taylor, Issue #1981)
  - Configure with `WithConnectionFactory(sp => ...)`, or with `WithDataSource(sp => ...)` when a `DbDataSource` is available (.NET 8+)
  - The factory is asked for a connection once per migration processor (per connection), not once per command, which makes rotating credentials such as Azure Entra ID or AWS RDS IAM tokens work as expected
  - Pass `ownsConnection: false` to `WithConnectionFactory` when the application keeps ownership of the connection, in which case the processor neither closes nor disposes it
  - Design rationale is recorded in [`adr/proposed/ConnectionManagement.md`](adr/proposed/ConnectionManagement.md), including how a `DbDataSource`-based design would work

### Changed

- .NET 11: `FluentMigrator.DotNet.Cli`, `FluentMigrator.MSBuild` and `FluentMigrator.Runner.SqlServer` target `net11.0` (Issue #2430)
- `FluentMigrator.MSBuild`: the build targets that NuGet imports automatically now load the `Migrate` task. They pointed at `build/tasks/<tfm>/` instead of `tasks/<tfm>/` in the package, so `<Migrate>` failed with MSB4062 unless the project declared its own `UsingTask`. The package also gains the missing `build/net10.0` targets. Found by Copilot review on PR #2431
- SAP HANA support now uses the `Sap.Data.Hana.Net.v8.0` and `Sap.Data.Hana.Net.v10.0` NuGet packages, and HANA registration was removed from the .NET Framework console and MSBuild runners.
- `FluentMigrator.DotNet.Cli` no longer depends on AutoMapper. The single `MigratorOptions` copy it performed is now generated at compile time by [Mapperly](https://mapperly.riok.app/), which removes a runtime dependency from `dotnet-fm` along with AutoMapper 15's commercial licence requirement and [CVE-2026-32933](https://github.com/advisories/GHSA-rvv3-g6hj-g44x). `Setup.BuildServiceProvider` no longer registers `AutoMapper.IMapper` in the service collection.
- The repository moved to NuGet Central Package Management. All package versions now live in `Directory.Packages.props` at the repository root; project files declare package references without a `Version` attribute. This is a build-infrastructure change only - the versions the shipped packages depend on are unchanged.
- Processor constructors taking an `IConnectionStringAccessor` are obsolete; use the overloads taking an `IMigrationConnectionFactory` instead.
- `GenericQuoter.UnQuote` no longer throws `ArgumentException` for a bracket-quoted SQL Server name such as `[dbo]`; SQL Server has no escape for `[`, and the empty search string made `string.Replace` throw. Found by the PR #2370 tests
- PostgreSQL index extensions can follow `UsingBrin()`, `UsingGin()` and the other index methods: `.WithOptions().UsingBrin().AsConcurrently()` threw `InvalidOperationException`, because the index-method builder didn't expose the index's additional features. The messages for `AsConcurrently` and `AsOnly` misuse no longer name `Include`. Found by the PR #2370 creation-script tests
- Binary values (`byte[]` in `Insert`, `Update` and `WithDefaultValue`) are written as Oracle `hextoraw('0102')` and Firebird `X'0102'`. Both used the generic `0x0102`, which Oracle rejects and Firebird reads as an integer, storing different bytes. Found by the PR #2370 creation-script tests
- Firebird: a `DateTime` value with no time of day is written as a date only (`'1991-08-25'`), because Firebird 4 rejects `'1991-08-25 00:00:00'` for a `DATE` column. Date-only strings still convert to `TIMESTAMP`. The format is now culture-invariant. Found by the PR #2370 creation-script tests
- Oracle: `Alter.Table(...).WithDescription(...)` ends its `COMMENT ON TABLE` statement with `;` like every other statement, so a script runs it on its own instead of joining it to the next statement. Found by the PR #2370 creation-script tests
- Version tables with `CreateWithPrimaryKey = true` no longer get a unique index. The primary key already carries `UniqueIndexName`, so the index with the same name failed on SQL Server and PostgreSQL when the version table was created; the 7.2.0 fix made that index non-clustered but kept the name (Issue #2051 by @zane-gers, diagnosed by @DevFearScar; found by Copilot review on PR #2370)
- Connectionless runs script migrations marked `BreakingChange = true` without `AllowBreakingChange`, as preview mode does. The connectionless processor has no database to break; it threw unless `--preview` was also set. Found by Copilot review on PR #2370
- Db2: `.Identity()` is written `GENERATED ALWAYS AS IDENTITY`, as on Oracle 12c and PostgreSQL 10. It was `AS IDENTITY`, which Db2 rejects, so no table with an identity column could be created. Found by Copilot review on PR #2370
- Db2: `SequenceExists` reads `SYSCAT.SEQUENCES`; it always returned `false`, so `Schema.Sequence(...).Exists()` never found one. Without a schema it looks in the current schema. Found by Copilot review on PR #2370
- Db2 LUW: `AsString` and `AsFixedLengthString` columns (`VARGRAPHIC`, `GRAPHIC`, `DBCLOB`) no longer get `CCSID 1200`. A Unicode database, Db2's default since 9.5, rejects the clause (SQL0622N), so no table with such a column could be created there, the version table's `Description` among them; graphic strings in a Unicode database are UTF-16 already. In a non-Unicode database they now take the database's graphic code page. Db2 for i (`Db2ISeries`) still writes `CCSID 1200`. Found by the PR #2370 creation-script tests, the first to run against Db2 in CI
- Db2: three more statements Db2 rejected. Binary values are written `BX'0102'` (Db2 has no `0x0102`); `Create.Sequence(...).IncrementBy(n)` writes `INCREMENT BY n` (Db2 requires `BY`); and `Create.Column` of an XML column no longer appends a bare `DEFAULT`, which Db2 doesn't allow on XML (SQL0628N). Found by the PR #2370 creation-script tests
- The reusable `migration-preview.yml` workflow passed `--outputFileName`, which dotnet-fm does not have, so every run failed with "Unrecognized option '--outputFileName'". It now passes `--output=<file>`. The dotnet-fm docs that showed the same option are corrected (PR #2370)
- Db2 finds its provider again. The factory looked for assemblies named `Net.IBM.Data.DB2.Core` and `Net.IBM.Data.DB2`, but `Net.IBM.Data.Db2` is the package name; the package (and its `-lnx` and `-osx` variants) ships `IBM.Data.Db2.dll`. On .NET it now loads `IBM.Data.Db2`, then the older `IBM.Data.DB2.Core`; on .NET Framework, the Db2 client's `IBM.Data.DB2`; and Db2 for i, `IBM.Data.DB2.iSeries` again. Not in a release: the names changed during 9.0 development. Found by the Db2 container that PR #2441 runs monthly

#### `dotnet-fm` now uses the Oracle beta ADO.NET driver

Oracle plans to release a non-beta version of the driver in Q3, but
it's the only Oracle driver that works under Linux/MacOS. The console
tool (`Migrate.exe`) is more Windows-centric and will therefore keep
using the standard Oracle ADO.NET library. The `dotnet-fm` is mostly
used on non-Windows platforms and is therefore predestinated to use
the new beta driver.

The statement from Oracle can be found on the
[Oracle website](http://www.oracle.com/technetwork/topics/dotnet/tech-info/odpnet-dotnet-ef-core-sod-4395108.pdf).

The console tool will switch to the new driver when it becomes stable.

#### New configuration options

```c#
var services = new ServiceCollection()
    .AddFluentMigratorCore()
    .ConfigureRunner(rb => rb
        .AddSQLite()
        .ScanIn(typeof(YourType).Assembly));
        // There is a fluent interface to configure the targets for ScanIn
```

Configurations for `ScanIn(assemblies)`:

```text
--+-------------------------------------------+->
  |                                           ^
  |                                           |
  +- For -+- All() ---------------------------+
  ^       |                                   ^
  |       |                                   |
  |       +- Migrations() ------------+-->+-->+
  |       |                           ^   |
  |       |                           |   |
  |       +- VersionTableMetaData() --+   |
  |       |                           ^   |
  |       |                           |   |
  |       +- EmbeddedResources() -----+   |
  |                                       |
  |                                       v
  +<--------------------------------------+
```

Example:

```c#

    .ConfigureRunner(rb => rb
        .AddSQLite()
        .ScanIn(typeof(YourType).Assembly)
            .For.Migrations()
            .For.EmbeddedResources());
        // There is a fluent interface to configure the targets for ScanIn
```

### Additional information

#### Connection string handling

The library assumes that in `ProcessorOptions.ConnectionString` is either a connection string or
a connection string identifier. This are the steps to load the real connection string.

- Queries all `IConnectionStringReader` implementations
  - When a connection string is returned by one of the readers, then this
    connection string will be used
  - When no connection string is returned, try reading from the next `IConnectionStringReader`
- When no reader returned a connection string, then return `ProcessorOptions.ConnectionString`

The connection string stored in `ProcessorOptions.ConnectionString` might be overridden
by registering the `IConnectionStringReader` instance `PassThroughConnectionStringReader`
as scoped service.

When no connection string could be found, the `SelectingProcessorAccessor` returns
a `ConnectionlessProcessor` instead of the previously selected processor.

#### Instantiating a migration runner

```c#
// Initialize the services
var serviceProvider = new ServiceCollection()
    .AddLogging(lb => lb.AddFluentMigratorConsole())
    .AddFluentMigratorCore()
    .ConfigureRunner(
        builder => builder
            .AddSQLite()
            .WithGlobalConnectionString(connectionString)
            .WithMigrationsIn(typeof(AddGTDTables).Assembly))
    .BuildServiceProvider();

// Instantiate the runner
var runner = serviceProvider.GetRequiredService<IMigrationRunner>();

// Run the migrations
runner.MigrateUp();
```

This adds the FluentMigrator services to the service collection and
configures the runner to use SQLite with the given connection string,
announcer and migration assembly.

Now you can instantiate the runner using the built service provider and use
its functions.
